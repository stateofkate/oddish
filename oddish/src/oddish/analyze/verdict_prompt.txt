Decide whether to accept or reject the benchmark task after classifying every listed trial. Accept means the task works and can stay in the benchmark. Reject means a person must fix the task first.

Use the enclosing QA brief's authoritative evidence manifest, baseline evidence, source-audit status and findings, and the classifications you just produced. Do not invent a missing baseline or source-audit result.

## THE LABELS

Each analysis gives its trial one label. A label is a claim from that analysis, not a verified fact.

* GOOD_SUCCESS — the agent's own work earned the pass. The label alone does not prove that the task has no defect.
* GOOD_FAILURE — the agent's own work decided the failure. The label alone does not prove that the task is fair.
* BAD_SUCCESS — the pass does not count. The agent cheated, copying solver-visible text would also pass most of the checks, or the tests accepted work that breaks a stated requirement. The task has a problem.
* BAD_FAILURE — a task defect, not the agent's work, decided the failure. The task has a problem.
* HARNESS_ERROR — the infrastructure broke the run, so the run says nothing about the task. One exception: the subtype `hidden_file_leak` means the task exposed hidden files, and that is a task problem.

## STEP 1: LOOK FOR AN IMMEDIATE REJECTION

Six kinds of evidence reject the task on their own. Look for them first. If you find one, reject the task. Good results from the other trials do not cancel it.

* Any reported task defect from the source audit or an execution review, including historical lower-severity findings. Every newly reported defect has tier `must_fix`. This is a delivery requirement; it does not establish causation for an execution. A delivery acknowledgment permits an exception without making the task defect-free.
* A used leak. A trial read the hidden tests, the solution, or other files the task must keep hidden (subtype `hidden_file_leak`, `test_inspection`, `oracle_copying`, or `unintended_access`).
* An answer in the task text. A trial has the subtype `solution_leaked_in_instruction`: copying solver-visible text without the requested computation passes most of the checks. A method, formula, convention, fixed parameter, or source document that the task gives the solver to use is an input, not an answer. The task measures copying, so every pass is meaningless.
* A found leak. A `must_fix` finding with the dimension `info_leakage`, from the source audit or from a trial. The finding counts even if no trial used the leak.
* Weak tests. A trial measured that the tests also pass work that breaks a stated requirement (subtype `permissive_tests` or `minimal_compliance`). Example: the untouched base model already scores above the pass threshold. Weak tests make every pass meaningless, including the ones labeled GOOD_SUCCESS.
* A failed baseline. The nop baseline changes nothing, so if it passed, the task was already solved. The oracle baseline applies the reference solution, so if it failed, the reference solution is broken.

## STEP 2: JUDGE THE REST

If step 1 found nothing, the remaining evidence is opinion: a trial label that claims a task problem without a reported finding, like "the instruction is unclear" or "the tests are too strict". A reported finding always belongs to step 1. One trial's opinion can simply be wrong. Trust an opinion only when most trials agree on it. Harness errors say nothing, so leave them out when you decide what "most trials" means.

Three rules:

1. A difficult task is not a bad task. A benchmark works best when only 10-40% of trials pass, so failures are expected. The pass rate alone never decides the verdict.
2. One fair success proves the task can be solved.
3. When a trial claims the instruction is missing information, check the solver-visible starting files. If one states it, or declares it with the exact name and the same signature or argument count that the test uses, ignore the claim, even if the agent never opened that file.

The decision: reject if most trials show the same task problem, with clear evidence. Accept in every other case. A run where every trial fails, a mixed run, or a single BAD label — all of that is normal for a difficult task.

Before you accept, read the `evidence` and `root_cause` of every trial. If one cites a task defect by file and line, check that line. If the defect is real, treat it as a reported finding and reject, even when no trial listed it in `action_items`.

## STEP 3: SET THE CONFIDENCE

* An immediate rejection is high confidence. One exception: if the only evidence is a single trial claiming weak tests, and the source audit has no matching `must_fix` `verifier` finding, use medium.
* A rejection because most trials show the same problem is high confidence.
* An accept is high confidence when the trials agree, and low when they disagree.

## VERDICT FIELDS

The enclosing QA brief owns the output file and JSON structure. Fill its `verdict` object as follows:

* Write for the task's author, who reads this once and has seen none of the analyses. Use short sentences, plain words, and no jargon.
* Wrap every code name in backticks: files, tests, functions, variables, config keys. Use no other formatting.
* `primary_issue` — null when you accept. When you reject, state the problem with a count: "3/4 trials fail because `test_io` compares output byte for byte". Start with "CRITICAL:" when a baseline failed.
* `recommendations` — none when you accept. When you reject, one fix per distinct problem, at most five, most common problem first, no duplicates. A fix keeps the task's goal, inputs, workload, and tolerances. Never recommend telling the solver where the problem is or how to fix it (the file to edit, the function that holds the bug, the algorithm). Never recommend shrinking inputs or removing a check of a requirement that the instruction or a solver-visible starting file states. Prefer fixing the test over adding to `instruction.md`. Recommend an `instruction.md` addition only when the test must keep a name, signature, or file path that no solver-visible starting file declares; the addition states only that name, signature, or path. Never recommend adding expected values, exact message text, output layouts, or what a new parameter does. "Make `test_parse` accept any whitespace instead of matching the reference byte for byte" is a fix; "improve the instructions" is not.
* `reasoning` — what the trials showed. If you rejected immediately, name the evidence. If you disagree with a trial's label, name the trial and say why.
